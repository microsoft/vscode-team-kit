# The diagram catalog

Generated by `prs catalog --sheet` from `catalog/*.js`. [catalog.png](catalog.png) shows every treatment, numbered as below, each with its own demo from a made-up PR: use it to see what a treatment looks like, never as content to reuse.

## title: the fixed opening frame (always the first beat)

### 1. `title.frame`: Title frame

Always the first beat. Fixed design: PR number, your short headline, the PR title, author, state, and a per-file "What changes" card.

Picture 1 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `headline` | label: what the PR does in 4-8 plain words (not the PR title) |
| `at` | { author, stats, state }: times; default to the cues of the same names |

## concept: a problem, a mismatch or a few ideas side by side

### 2. `concept.mismatch`: Have vs need

The problem is a mismatch: what something is vs what is required (a token, a format, a permission, a version). The requirement (need) shows first, by default 0.4 s in, then what there is (have) and its rows: narrate the requirement first, or time need.at to its words.

Picture 2 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `have` | { icon, title, rows: [{ key, value, ok, at }] }  (2-3 rows) |
| `link` | { label, verdict: { text, tone }, at } |
| `need` | { icon, title, sub, tone, requirement: { label, text }, at } |
| `footer` | { lead, note, at, items: [{ icon, title, mono, label, value, sub, chip, tone, at }] }  (optional, 1-4 items) |

### 3. `concept.pillars`: Numbered pillars

Two to four ideas, parts or reasons of equal weight ("three things change").

Picture 3 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `items` | [{ icon, title (about 3 words), text, code (a short code name under the text, drawn as code: ident() or quote(), not code()), at }]  (2-4) |

### 4. `concept.statement`: Statement

The point fits in one sentence ("the bug: X happens because Y"). Good for small PRs and for the problem beat.

Picture 4 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `parts` | [text \| { text, mark: tone, at }]  (the sentence; marked parts highlight at their time) |
| `chips` | [{ icon, text, tone, at }]  (0-4; they wrap onto a second row past the width, so keep them short) |

## exchange: messages between parties: a protocol, a handshake, a request and its reply

### 5. `exchange.journey`: Packet journey

One request or value moving through 3-5 places, where what happens at each stop matters more than strict call order.

Picture 5 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `packet` | { text, icon, tone }  (what travels) |
| `nodes` | [{ id, icon, title, sub, tone }]  (3-5, left to right) |
| `hops` | [{ from, to, label, result, resultTone, at }]  (each a curve between two nodes; result shows on the arrival node) |

### 6. `exchange.lifelines`: Sequence diagram

A protocol or handshake with 2-4 parties and 2-5 ordered messages; best when the order of calls is the point.

Picture 6 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `tag` | label (e.g. the spec name) |
| `tagAt` | time |
| `parties` | [{ id, icon, title, sub, tone }]  (2-4, left to right) |
| `steps` | [{ from, to, request, requestSub, mono, reply, replyTone, at, replyAt, badgeAt }]  (2-5) |
| `skip` | { at, note, from: stepNumber (default 2), alt: { step, text } }  (optional: later steps are conditional) |
| `code` | { block: code(...), title, rows (default 3), steps: [{ at, from, to }] }  (optional) |

## rules: a rule applied to cases: validation, filtering, permissions

### 9. `rules.matrix`: Comparison matrix

A rule that compares several fields of each case against a reference (origin, version, scope). Cases come from the PR’s tests.

Picture 9 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `tag` | text (e.g. the function) |
| `tagAt` | time |
| `tagMono` | bool |
| `columns` | [{ id, label, width }]  (2-4 data columns; widths in px, total about 1290) |
| `verdictLabel` | label for the verdict column |
| `reference` | { cells: { [column]: text }, verdict: text } |
| `rules` | [{ column, text, tone, at }] |
| `rows` | [{ cells: { [column]: text }, pass: { [column]: bool }, ok, verdict, why, at } \| { whole: text, ok, verdict, why, at }] |
| `code` | { block: code(...), title, note, rows }  (optional) |

### 10. `rules.sieve`: Gates

A series of checks that filter cases (2-3 gates, 2-5 cases): which ones make it through, and where the others stop.

Picture 10 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `gates` | [{ label }]  (2-3, in order; short labels: they shrink together when the gates are close) |
| `pass` | { label, icon }  (the zone for cases that pass every gate) |
| `cases` | [{ text, mono, stopsAt: gate number (1-based) or null when it passes, why, tone (a stopped case is red, a passing one green; set it when stopping is the intended outcome), at }]  (2-5) |

### 11. `rules.stamps`: Verdict stamps

A rule shown through 3-6 concrete cases that each get a clear yes or no.

Picture 11 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `rule` | { icon, text, at }  (the rule in one line) |
| `cases` | [{ text, mono, sub, ok, verdict (2-3 words on the stamp), why (a few words beside it), at }]  (2-6) |

## compare: behavior before and after the change

### 12. `compare.split`: Before and after

Behavior that differs on 2-5 aspects (what the user sees, what is sent, what is cached). The narration names the aspects in order, a sentence each, and each row lands on its word; or it tells the old way first and turns on "Now" (afterAt: the whole new column then).

Picture 12 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `before` | { title, icon } |
| `after` | { title, icon } |
| `rows` | [{ aspect, before, after, changed (default true), mono, at, afterAt }]  (1-5; mono is for the whole row) |
| `afterAt` | time the new column appears, row after row (optional: by default each row's new side follows its old one) |
| `takeaway` | { text, tone, at }  (optional) |

### 13. `compare.wipe`: Wipe reveal

One screen, list or result that looks different after the change; the viewer sees it flip in place. The narration says what it was, then what it is now: the wipe lands on the word that turns ("Now"). The whole panel turns at once, and its items flip in place: give before and after the same rows in the same order.

Picture 13 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `before` | { title, icon, items: [{ icon, text, tone, mono }] }  (2-6 items) |
| `after` | { title, icon, items: [...] } |
| `at` | time of the wipe |
| `note` | { before, after }  (labels under the panel) |

## architecture: where the change reaches: components, processes, layers

### 14. `architecture.layers`: Layer stack

The change sits at some levels of a layered system (for VS Code: base, platform, editor, workbench, extensions). Shows which layers move and how a call crosses them.

Picture 14 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `layers` | [{ title, sub, icon, touched, note, at }]  (3-6, top to bottom; note = what changes there) |
| `path` | { text, icon, through: [layer numbers, 1-based], at }  (optional: a marker travels through these layers) |

### 15. `architecture.map`: Reach map

Something (a token, a setting, a cache) now flows to several request types or processes. Shows every place it reaches.

Picture 15 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `source` | { icon, title, sub, tone, chip: { icon, text } } |
| `target` | { icon, title, sub, tone } |
| `lanes` | [{ title, sub, at, key: bool }]  (1-4 labeled arrows from source to target) |
| `branch` | { label, sub, at, nodes: [{ icon, title, sub, tone, at }] }  (optional, 1-3 nodes) |
| `aside` | { label, at, rows: [{ lead, value, text, tone, strikeAt }] }  (optional, 1-2 rows) |

### 16. `architecture.zones`: Process zones

The change spans processes, machines or owners, and what crosses the boundary (IPC, a protocol, a file) is the point.

Picture 16 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `zones` | [{ title, sub, tone, items: [{ id, icon, title, sub, at }] }]  (2-3 zones, 1-3 items each) |
| `links` | [{ from: itemId, to: itemId, label, mono, at, tone }]  (0-4; link items on the same row of neighbouring zones: a link between rows runs its label over other parts) |

### 17. `code.diff`: Diff with callouts

The change is small and the exact lines tell the story (a condition flipped, a guard added, a value changed). Up to ~18 diff lines.

### 18. `code.walkthrough`: Code walkthrough

One function (up to ~30 lines) is the heart of the PR; 2-4 notes explain its parts in order.

Picture 18 in [catalog.png](catalog.png).

| param | what |
| --- | --- |

## state: states and transitions: a lifecycle, a state machine

### 21. `state.track`: State track

Something moves through 3-5 states (signed out -> negotiating -> authorized; queued -> running -> done), maybe with a failure state.

Picture 21 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `states` | [{ title, sub (about 30 characters: one line), icon, tone, at }]  (3-5, in order) |
| `edges` | [{ label }]  (labels of the transitions between consecutive states; optional) |
| `marker` | { text, icon }  (what moves) |
| `fail` | { from: state number, title, sub, tone (red by default; neutral for an end that is not a failure), icon, at }  (optional dead end below a state) |

## status: scope, tests and what is still open

### 23. `status.board`: Now, next, later

The closing beat when the PR is one step of a larger plan: what lands now, what follows, what is open. Text only: for places to start reading (code references), use status.checklist.

Picture 23 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `columns` | [{ title, tone, icon, items: [{ text, sub, at }] }]  (2-3 columns, 1-4 items each) |

### 24. `status.checklist`: Checklist + start here

The closing beat: what is in scope, what is left for later, how it is tested, and the 1-3 places to read first.

Picture 24 in [catalog.png](catalog.png).

| param | what |
| --- | --- |
| `eyebrow` | label |
| `title` | label |
| `items` | [{ icon, tone, title, sub, at }]  (2-5) |
| `read` | { label, refs: [{ code: code(file, { anchor }), title, what, at }] }  (optional, 1-3; without at, the refs light up from a third of the way into the beat) |
